# 客服回复评估标准 v1.0

标准 ID：`customer-support-review-v1.0`。记录日期：2026-10-04（北京时间）。
这是对本次 27 条 AI 客服专家代评口径的详细记录，作为后续对比的校准基线。
评分仍包含判断，不因形成文档就成为完全客观测量；通过固定证据、尺度、边界案例和复核流程降低漂移。
本版本不重新评分，不修改旧工作簿，也不新增或读取 sealed_test。

## 1. 评估对象和证据范围

评估单位为一条客户问题及模型的完整生成回复，包含截断、占位符和语言瑕疵。按真实显示给客户的文本评分，不替模型补全。
评的是单轮回复能否正确理解并推进诉求，不要求单轮完成必须依赖身份验证、业务后台或更多信息的任务。

证据优先级：客户原话及已提供信息 → 本轮明确提供的有效业务资料或工具结果 → 生成原文。
参考回复用于理解任务，不是事实核验资料、唯一正确回答或必须匹配的模板。
数据中的 intent 标签只用于分组和审计；当措辞与标签不完全一致时，以客户实际表达为判断依据。
不得虚构网站入口、真实政策、后台权限、订单状态或客户心理来补足证据。

本次未提供真实商户政策、网站页面或后台查询结果，因此业务事实均未获外部核实。
“可能着急、烦躁或担心”只能作为措辞支持的解释，不是对客户心理状态的确定判断，不另设心理分数。

## 2. 五个字段的尺度

| 字段 | 范围及方向 | 定义 |
| --- | --- | --- |
| `intent_score_0_2` | 0–2，越高越好 | 是否识别并回应客户的主要动作、对象及问题性质 |
| `helpfulness_score_0_2` | 0–2，越高越好 | 是否提供有效下一步或必要、可回答的澄清 |
| `fluency_score_0_2` | 0–2，越高越好 | 文字是否连贯、完整、易于理解 |
| `repetition_0_1` | 0/1，1=问题 | 是否存在明显无新增信息的重复或重复索取 |
| `unsupported_claim_0_1` | 0/1，1=风险 | 是否出现缺证据的具体业务断言、能力或结果保证 |

未评必须留空。0 是实际分数，不代表缺失。五项分别判断，不合并为未定义的“总分”。
同一缺陷可以影响多个不同维度，但每个影响都要说明；不得机械地让所有维度一同扣分。

### 2.1 意图：是否答对客户真正要做的事

- **2**：核心动作及对象正确，区分查询、申请、下载、修改、排障等。缺少步骤但没有改写任务，通常仍可得 2，步骤问题记在帮助分。
- **1**：大类相关，但忽略关键限定、将排障当常规操作、将找说明当执行操作，或引入改变任务对象的假设。
- **0**：主要回答另一件事，或没有实质回应客户核心需求。

判断顺序：提取“动词 + 对象 + 关键限定” → 查看生成实际做什么 → 比较是否发生任务偏移。
客户已有编号却被丢弃，若主任务仍正确，可保留意图 2，同时降低帮助分并记实体错误。
不能只因回复出现 refund/order 等关键词就给意图满分。

### 2.2 帮助：客户读完后能否合理推进

- **2**：有适当、可执行的下一步；或缺信息时提出必要且相关的澄清，不强求单轮解决。允许有可改进但不阻碍首轮推进的细节。
- **1**：提供部分路径或笼统相关追问，但漏关键动作、未处理实际障碍、缺少可用值，或增加不必要交互负担。
- **0**：无有效推进，或主要建议具有明确误导风险，如无依据支付方式列表、未经核实直接承诺配送、将免费诉求带向付费升级。

合理澄清：到货时间缺订单/物流标识时询问该标识；删除部分商品时询问具体商品；付款/注册失败时询问错误信息。
低效澄清：重复索取已经出现的信息；将未提及的报错作为前提；客户要入口却只说“请提供更多详情”而不给可用路径。
不要求每个追问都列完未来全部问题。例如商品名称的首轮询问可以满分，数量可下一轮确认。
礼貌、篇幅、编号步骤和“我们会帮助你”本身不能提高帮助分。
投诉/退款中的具体承认、非责备措辞有助于推进；缺道歉不自动扣分，若回复同时笼统且增加阻力则记录影响。

### 2.3 通顺：只判断语言，不替代事实质量

- **2**：结构连贯、句意清楚，没有明显破坏理解的语病。内容错误、实体错误、重复或过度热情可以单独记，不自动将通顺降为 1。
- **1**：大体可理解，但有明显残句、搭配错误、句式重复导致语病、异常衔接或结尾被截断。
- **0**：多数关键内容无法理解，严重混乱或碎片化，难以辨认所给建议。

例如 `may have a seamless`、`using Apple users`、`a form or a form` 为 1 的锚点。
本次 `account!I` 缺空格且伴随夸张、重复表达的整体回复记 1；单个标点瑕疵不设自动扣分规则。
同一实体重复导致内容冗余但句子可读时，通顺可为 2，重复标记为 1。
达到 token 上限而出现残句，按已输出文本记语言缺陷，同时注明“长度上限截断”，不能直接归因为模型内在语言能力。

### 2.4 重复：无新增信息的复述

- **1**：重复短语、句意、步骤或索取已有信息，明显增加负担；或相邻候选相同，如 `X or X`。
- **0**：无上述重复；正常复述需求、必要保留订单标识、前后具有不同作用的内容不算。

本次采用相对敏感的阈值：不仅循环才记 1。相邻句再次说 `would like to purchase`、多次说 smooth experience 也记 1。
`track_order` 在复述已有订单号后又索取订单号，属于交互重复，记 1。
不能只按词频或字符串重复次数自动评分。长回复不必然重复，短回复也可能重复。

### 2.5 无依据：业务断言与保证的风险

- **1**：存在缺有效依据的商户特定事实、确定流程或结果保证，尤其影响支付、配送、退款、账户权限、资费或隐私。
- **0**：未发现符合本版本阈值的断言；仍可有“业务入口待核实”等备注。0 不表示事实已验证、合法或业务上一定安全。

标记 1 表示缺证据风险，不表示已证明虚假。不要把“无法证实”写成“经核实错误”。

| 断言类型 | 本次 v1 判定 | 判定依据与边界 |
| --- | --- | --- |
| 列出商户接受 Visa/PayPal 等、承诺配送指定城市 | 1 | 具体业务覆盖事实，未给商户证据，客户可能据此付款或下单 |
| 账户页有自助注销，登录后经邮箱重置 PIN，反馈页必有表单 | 1 | 将特定业务操作流程当成确定事实，缺真实页面或流程依据 |
| 页面必包含费用/退款的 `all the information` | 1 | 对信息完整性作强断言，不只是建议查看 |
| `issue a refund`、`ensure a smooth resolution`、保证及时取消、隐私处理保证 | 1 | 承诺业务结果或处理能力，未提供授权、工具或政策证据 |
| 有编号就 `will be able to give you an accurate estimate` | 1 | 本次将无查询资料情况下的准确性与能力保证列为风险；不是说所有预计时效都不可信 |
| 普通账单/地址导航建议，`should be able to find`，没有高影响结果保证 | 0，备注待核实 | 本次未将所有未核实页面名称一律记 1；有条件的通用建议与确定业务事实分开 |
| `I'm here to help`、`work towards resolving`、调查时的 promptly | 0 | 一般服务意愿，未断言已经办成、确定成功或具体截止时间 |
| 数据本来已有的订单号/营业时间占位符 | 不因占位符自动记 1 | 匿名化模板不是虚构具体值；未给可用营业时间可降低帮助分 |
| 加入 `for your wife`、假定客户遇到报错 | 用意图/实体或假设标签记录 | 客户事实误读不等于本字段所指的业务承诺；create_account 本次的 1 另有隐私保证依据 |

判定步骤：摘录原文断言 → 指明所需证据 → 查本轮是否存在有效证据 → 按上表区分建议、服务意愿与确定断言。
若以后接入真实业务资料，必须记录资料版本和适用范围；不得沿用“缺证据”结论而忽略新证据，也不得与无资料条件直接归因比较。

## 3. 特殊情况统一处理

1. **占位符与实体**：已有 `{{Order Number}}` 当作已提供的匿名化订单标识，不要求客户再给一次。输出未填营业时间仍不具实际帮助。客户提供 `37777` 后改成通用占位符，记实体丢失。不同人名字段不默认指同一个人。
2. **参考文本错误**：参考答案也可能丢编号、编造政策、过度热情。模型重复参考缺陷仍要记，不能靠文本相似免责。
3. **停止原因**：EOS 不代表正确。max_new_tokens 不自动全项零分；只评价实际影响，并保留停止原因作为独立证据。
4. **客户情绪**：粗口可提示烦躁，但不能假定人格、关系或心理疾病。共情建议必须服务于明确下一步，不奖励过度寒暄。
5. **隐私**：可询问信息类别、脱敏错误及必要订单标识；不鼓励在未说明安全渠道时收集敏感资料。安全建议作为备注，不新增隐私得分或事后改写五项尺度。
6. **多维问题**：流利但误导可为意图 2、帮助 0；合理澄清但伴随准确性保证可为帮助 2、无依据 1。不同维度并不互相抵消。

## 5. 每条评分的操作流程

1. 在看参考文本和模型成绩前，用一句话写出客户主要诉求、已给信息及关键限定。
2. 阅读完整生成，先独立打意图、帮助、通顺，再记录重复和业务断言。
3. 对缺陷摘录最短必要原文，说明如何影响客户下一步。需要资料才能判断时写清缺什么资料，不假装已核实。
4. 必要时读参考文本检查遗漏，但不以参考措辞或逐字一致作为判据。
5. 对照本文件边界表和历史锚点复核；对接近阈值的案例写明取该分数的理由，不用模型名或 loss 帮忙裁决。
6. 保存 ID、五项分数、错误标签、证据/改进建议、reviewer、评审日期、rubric ID 及相关版本/哈希。

备注模板：“客户诉求：……；证据：原文……；影响：……；改进：……；待核实：……”。
标记 1 的重复/无依据及低于 2 的前三项都应能找到具体理由；满分也不表示完美，不应写无证据的赞美。
常用标签：任务偏移、关键步骤缺失、未处理报错、实体丢失/替换、重复索取、语病、重复、截断、业务入口待核实、业务断言缺依据、结果保证缺依据、隐私保证缺依据。
标签辅助检索，不代替分数。遇到新问题可增加标签，但不得借此改变分数尺度。

## 6. 后续比较与汇总

- 固定同一批 ID、输入模板、tokenizer revision、上下文预算、解码方法及 token 上限；主动改变的因素另外记录，不得隐瞒。
- 尽量隐藏模型名、轮次、loss 和旧分数，先对打乱顺序的回复独立评分，再揭示配对结果，以降低预期偏差。
- 正式比较前用第 4 节锚点校准。多人评审先独立评分，保存分歧与裁决原因。AI 复评也可能不稳定，不声称是独立人工一致性。
- 三项均分 = 各项有效分之和 / 该项已评条数。重复率和无依据率 = 标记 1 条数 / 该项已评条数。每项同时报告分母，缺失不按 0 填入。
- 基线完整评估要求同一批 27 条五项均填写。若有漏项，不与完整批次直接声称改善；配对比较只用共同已评 ID，并报告覆盖情况。
- 不设事后权重或总分，不把五项随意相加。无依据率是风险标记率，不是经证实的幻觉率。
- loss 按记录中的回复及保留 EOS token 口径报告。不同数据规模/评估集、train 过程均值和轮末 dev loss 不直接混为同一个指标。
- 只有同一全量运行第 0–3 轮的全 dev loss 当前可作同集阶段比较；本次只评分第 3 轮，不推测前几轮生成得分。
- 每 intent 一条的 27 条是开发诊断，不能估计全 dev 的无偏质量、线上成功率或最终泛化；dev 已参与模型选择，sealed_test 继续封存。

## 7. 版本和复核记录

v1.0 固定为本次口径。修改阈值、字段含义、证据条件或锚点须另存 v1.1/v2，并写变更原因及受影响项，不静默编辑此版本。
需要采用新标准比较新旧模型时，对双方相同 ID 统一重评，另存新评分；不能新模型用新标准、旧模型继续用旧分。
复核最少记录：样本 ID、原分、新分、差异原因、评分人、日期、rubric ID。保留原始生成与旧评分。
本文件只固定程序和口径，不能保证不同评审或不同时间给出绝对相同的主观分数。
