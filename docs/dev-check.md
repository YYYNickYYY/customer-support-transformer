## 初始27条协议

v1 从冻结 dev 文件按实际 intent 分组，各选一条，共 27 条、11 个 category。
同 intent 内取 SHA-256(`42:样本ID`) 最小的样本，intent 按字典序排列。
不按回复长度、参考答案或模型表现筛选；不是随机代表全量 dev 的无偏质量估计。
样本 ID/category/intent/template_id、dev 哈希保存在 `artifacts/dev-check-v1/selection.json`，
该清单 SHA-256 保存在 freeze.json；更换 seed、修改清单或 dev 文件都会被拒绝。
先固定检查集，再生成，不覆盖已有评分或输出。

详细且版本化的评审口径、边界案例、校准锚点、汇总与重评流程见
[客服回复评估标准 v1.0](evaluation-rubric-v1.md)，标准 ID 为 `customer-support-review-v1.0`。
后续比较须记录所用标准版本；下表是摘要，边界判定以该版本文档为准。

逐条阅读问题和生成回复，参考回复仅作辅助，不能以逐字匹配代替质量判断。

| 人工字段 | 规则 |
|---|---|
| intent_score_0_2 | 0=错误意图/答非所问；1=大体相关但忽略关键诉求；2=准确回应意图 |
| helpfulness_score_0_2 | 0=无有效帮助或误导；1=部分帮助/关键步骤缺失；2=适当可执行或合理澄清 |
| fluency_score_0_2 | 0=难以理解；1=可理解但有明显语病；2=自然通顺 |
| repetition_0_1 | 0=无明显冗余；1=明显重复短语/步骤或循环 |
| unsupported_claim_0_1 | 0=未发现达到本版本阈值的缺依据业务断言；1=具体业务事实、能力或结果保证缺依据，不代表已证实为假 |
| error_tags | 错意图、漏关键点、重复、未结束、业务需核实、实体错误等，可多选文字 |
| notes / reviewer | 具体证据、需核实事项以及评分人 |

前三项高分更好，两个问题标记中 1 表示存在问题。未评留空，不填 0。
无法核实业务事实时，在 error_tags/notes 标记“业务需核实”，不假装已经验证。
不因为正常 EOS 就判为回答正确，也不因与参考文本不同就判为错误。
生成长度上限导致未结束需要单独记录，不能直接归因于模型能力。

评分应保持同一标准、同一批 ID 和解码参数，后续模型比较要匹配 ID，
保留旧评分，避免只展示改善的样本。可按 intent 汇总，但每 intent 只有一条，
结果是开发诊断，不是最终测试或业务可靠性保证。
